## 0. App anatomy

* Framework: Expo SDK 55 / React Native, expo-router file routes (`app/*.tsx`), zustand stores, axios (`package.json`, `AGENTS.md`). OTA via expo-updates plus APK self-update from GitHub Releases (`src/core/updates/*`).
* Layering: `app/<route>.tsx` is a 11-line shim -> `src/tenants/karen/features/<x>/<X>Screen.tsx` (UI) -> `src/tenants/karen/state/karen-<x>-store.ts` (zustand, validation, orchestration) -> `src/tenants/karen/api/karen-<x>-api.ts` (axios calls). The "Karen" tenant also serves `Demo`; tenants Kikwetu/Xflora/Mona/Tambuzi have their own drawers (`src/composition/drawer-resolver.ts:9-16`, `src/tenants/*/navigation.ts`). Tenant is derived from the instance URL (`src/core/tenant/instance-mapper.ts:24-54`, a hard-coded URL map incl. many dev LAN IPs).
* Drawer for Karen (`src/tenants/karen/navigation.ts`): Home, Scheduler, Issuing, Packing, Bunch Handover, Precooling, Staging, Loading, Bucket Logistics, Dispatch. Hidden routes: `configure-station`, `settings`, `debug-log`, `camera-scanner`, `camera-capture`, `biometric-lock`, `login`.
* API client `src/core/api/client.ts:8-59`: ONE axios instance, 30 s timeout, `Cookie: sid=...` header from AsyncStorage, base URL from AsyncStorage. NO retry, NO request queue, NO idempotency key. Errors are mapped by `mapAxiosError` (`client.ts:124-140`): Frappe `_server_messages` -> plain text (this is the text the worker sees), HTTP 503 / `SessionStopped` -> "The server is being updated. Please try again in a few minutes.", else `exc.message`, else exception class name, else axios message ("Network Error", "timeout of 30000ms exceeded").
* Auth: `POST /api/method/login` form login (`src/core/auth/api.ts:56-91`; the `mobileLogin` backend method `api.py:314` exists but the app does NOT call it - grep). Cookie stored in AsyncStorage (`StorageKeys.cookie`), plus email + PASSWORD stored in clear in AsyncStorage for biometric re-login (`src/core/storage/index.ts:13-18`, `auth/repository.ts:51-58`). Biometric lock screen `app/biometric-lock.tsx`. Roles fetched once at login via `getCurrentUserRoles` (`api.py:3196`) and cached - but `hasRole()` (`src/core/auth/store.ts:300`) is NEVER called by any screen (grep `hasRole|roles` outside core/auth = nothing). So: **no role gating at all in the app**; every logged-in user sees every drawer item and can call every endpoint. Who can do what is only limited by Frappe permissions on the server (most endpoints use `ignore_permissions` internally).
* Station (device-wide, not per user): `/configure-station` (`src/core/features/station/ConfigureStationScreen.tsx`, `core/tenant/user-station.ts`) stores `{userFarm, userGreenhouse}` in AsyncStorage `userStation`. Farm list = `GET /api/resource/Farm`, greenhouse list = `GET /api/resource/Warehouse` filtered by name prefix (`core/features/station/repository.ts:271-307`). `stationParams()` (`user-station.ts:218-223`) adds `station=<userFarm>` to many calls. Server maps station -> location: Karen farms -> "Karen"; everything else (Kapkolia and the remote farms trucking to it) -> "Ravine" (`api.py:_loading_location :2041`, `_station_location :2058`). This is the ONLY per-device scoping; it is the Karen-vs-Ravine split ("Karen and Ravine share teams, not orders").
* There is **no offline queue / sync** (see section 5.1). "Offline" in the app has two unrelated meanings: (a) the red banner when the device cannot reach the server (`core/network/store.ts`, `core/ui/OfflineBanner.tsx`), and (b) "Issued offline" = a bucket that physically went to a team without the issue scan (a paper/verbal step the app later reconciles, section 1.2).

### 0.1 Home / Packhouse dashboard (what management-ish info the floor already sees)
* `src/tenants/karen/features/dashboard/HomeScreen.tsx` -> `PackhouseDashboard.tsx` (714 lines) via `state/karen-dashboard-store.ts` -> `GET api.py:getPackhouseDashboardData` (`:6394`, params `date` default tomorrow, `station`). The mock management dashboard must not merely repeat these (they are packed-count based, not stage/wait based). Note "packers" there are derived from Farm Pack List owner (api.py docstring `:6404-6411`).

* Writes: none.

### 1.2 Issuing ("Issue from Coldstore")
* Files: `app/issuing.tsx` -> `features/issuing/IssuingScreen.tsx` (727 lines), `ReplacePicker.tsx` (301), `state/karen-issuing-store.ts` (745), `api/karen-issuing-api.ts`.
* Who: cold-store issuer / "Rosenta Issuer" / packer / line supervisor (roles per 01 doc, not enforced by the app). Station device must be configured? Issuing passes `station` to the list (`karen-issuing-store.ts:loadOrders`), and `stationParams()` to the bucket list; with no station set the server shows all locations.
* Steps (worker view):
  1. Choose delivery date (default tomorrow), optional item-group chip and team chip (canonical list from `getPackingTeams`; chip shows count of ready orders for that team today, 0 allowed).
  2. Pick an OPL from a dropdown. Dropdown rows are in server order: `issue_done` last, then scheduled before unscheduled, by sequence, team, name (`api.py:getReadySaleOrderItems` sort, `:3701`). Each row shows `order name - varieties (lengths)`, corner badge `"<Team> #<seq>"` or "Not scheduled", sub-line `OPL - customer - NN% issued (x/y bkt)`, and in red `[DRAFT] n not found - short NN%` (`IssuingScreen.tsx:127-168`).
  3. The bucket list for that OPL loads (`POST getReadySaleOrderItemsData`, `api.py:3720`): ONE row per bucket (the app merges per-box/per-line rows, `karen-issuing-store.ts:extractPackingList`), with shelf, variety, stem length, stems, "downgrade to" if bucket stem longer than ordered length, status: waiting-transfer (shows source farm), not found, issued (hidden by default behind "show issued"), plus progress bar issued/total.
  4. Scan a bucket QR (`ScanField` hardware scanner or camera `app/camera-scanner.tsx`). Accepts raw id, `{"bucket_id"}`, `{"id"}`, or legacy `{"BUCK-001":"bucket"}` (`extractBucketIdFromScan`). One scan issues ALL outstanding sale-order lines of that bucket on the OPL, sequentially, stopping at the first server rejection (`submitScan` loop, `karen-issuing-store.ts` ~`:500`).
  5. Toast "Issued <bucket>" or red alert with the server message. UI updates optimistically (marks lines issued, bumps issued %, moves a fully-issued order to the bottom of the dropdown list).
  6. Exceptions on the same screen: **Replace** a bucket (reasons Missing / Damaged / Wrong variety / Issued offline, `ReplacePicker.tsx`), **Complete short** (when every non-found bucket is issued), **Pack while waiting** (half or more of stems issued).
* Endpoints:
  * `GET getReadySaleOrderItems` (`api.py:3469`) list of OPLs for the date (Sales Order delivery_date) with issued progress, schedule place, `is_next`, `waits_for`, `pack_waiting`, short info. Listed only if it has an unissued bucket HERE (not still at a remote farm / on a truck, not another location's bucket) or is fully issued (shown at bottom). Submitted OPLs plus draft OPLs whose transfers have all settled.
  * `POST getReadySaleOrderItemsData` (`api.py:3720`).
  * `POST issueBucketToSaleOrderItem` (`api.py:4878`) per line.
  * `GET /api/method/upande_packhouse.api.offline_issue.replacement_options`, `POST ...replace_for_issuing`, `GET ...issued_offline_info`, `POST ...mark_issued_offline` (`api/offline_issue.py:629, 671, 725, 742`).
  * `POST completeOplShort` (`api.py:2140`), `POST /api/method/pack_while_waiting_replacement` (Server Script `server_scripts/pack_while_waiting_replacement.py`).
* Records written by one issue scan (`issueBucketToSaleOrderItem`): `Stock Entry.custom_issued_to = sale_order_item` (`db.set_value`), `Pick List Item.issued = 1` for the line's rows (`db.set_value`, no time/user), Shelf Item decremented or deleted (+ `Shelving Log` reason "Issued to Sales Order", `removed_on`, `shelved_by = session.user`, `api.py:~5160-5190`), `Bucket Allocation Status` row `issued=1` + recompute, stock hop `post_issue_to_packhouse` (a Stock Entry), then `_submit_for_packing` (a DRAFT OPL is auto-submitted once nothing is on a truck and issued >= Pack While Waiting % or fully issued, `api.py:2100`). **PLI.issued_at / issued_by are NOT stamped by the scan** - a 5-minute scheduler backfills them from the row's `modified` (01 doc step 3). The scan itself calls `frappe.log_error("Issuing from coldstore payload", payload)` on EVERY call (`api.py:4883`) - see 5.3: an Error Log row per scan with creation time and owner.
  * Replace: creates/updates `Bucket Replacement` (reason, notes), swaps the PLI bucket; Mark issued offline sets `Pick List Item.issued_offline = 1` after running the same issue logic (`offline_issue.py:742-776`) - this is the paper-step reconciliation: the bucket was handed out without the scan and the issuer records it afterwards.
  * Complete short: `OPL.short_accepted = 1, short_stems`, submit (if draft), `OPL.add_comment("Info", "Completed short by N stems (P%): buckets -- reason")` (`api.py:2205-2212`). The app never sends a `reason` (`completeShort(oplName)` call in the store passes none) - so the reason text is always empty. Pack while waiting: submit if draft, `pack_issued_now = 1` (no modified bump), and an Info comment "Packing what was issued: P% issued...".
* Gates / refusal messages the worker sees (verbatim):
  * Schedule order (HTTP 409): `Schedule order for team {team}: issue #{n} first. #{n} isn't fully issued yet, so #{seq} can't be issued before it.` (`api.py:4905-4909`). Rule `_schedule_blockers(opl, "issue") :3266`: per team, only earlier orders at the SAME location (`_stock_locations`) that are not fully issued block (not-found buckets don't count); bypass = Production Settings `allow_issue_out_of_sequence`. NOTE the issuing app does NOT pre-block or grey out: `waits_for` is mapped into the store (`karen-issuing-store.ts:110,216`) but never read by `IssuingScreen.tsx` (grep `waitsFor` only hits the stores). The issuer only discovers they are out of sequence when a scan returns the 409 above. Every such 409 is therefore a "worker tried to work out of order" event (and lands in Error Log, see 5.3).
  * Local pre-checks (no request): `Pick a pick list before scanning.`; `Could not read a bucket ID from that scan.`; `Bucket X isn't allocated to OPL.`; `Bucket X has no Sale Order Item - server data is incomplete.`; `Bucket X is already issued.`; `Bucket X is waiting for transfer from <farm>. Issue it once it arrives and is shelved.` (same text also from the server, 409 `waiting_transfer`, `api.py:4930-4950`).
  * Server: `Error: Bucket ID is required`, `Error: Sale Order Item is required`, `No stock entry found with bucket ID: X` (404), `Stock Entry X is already issued to a DIFFERENT sale order item (Y)` (409), `Error issuing bucket: <exception>` (500).
  * Complete short: `No bucket of X is marked not found.`, `Bucket(s) ... are still coming by truck.`, `Issue bucket(s) ... first.` (`api.py:2160-2185`).
  * Pack while waiting: `Only P% is issued; packing can start from N%.`, `Bucket(s) ... are still coming by truck.`, `X is fully issued.`, `X is already completed short.`, `X is already packing what was issued.`
  * Replace: `Bucket X is not on any shelf.`, `Bucket X holds <variety>, not <variety>.`, `Bucket X is not shelved at <farm>.`, `Bucket X is Ncm, shorter than...`, `Bucket X is allocated to another order.`, `Bucket {0} is at {1}, not at {2}.`, `... was issued to {team (order)}, not this line. Replace it instead.` (`offline_issue.py:118-153, 703, 751-756`).
* What the floor sees: dropdown with per-order issued %, bucket counts, not-found/short %, team + schedule place; per OPL a progress bar and the list of buckets still to issue with shelf location (so issuer can go to the shelf); "waiting for transfer from <farm>" badges. It does NOT show elapsed time, nor who issued what, nor time since the order became issuable.
* Offline/duplicates: scan is a plain POST; if the response is lost (timeout/airplane) the worker sees an error and can rescan. Backend is idempotent per line (comment `api.py:4985-5000`: "Every step below is independently idempotent"), so a rescan after a lost response will re-run harmlessly and return success, but it moves `Pick List Item.modified` (which is the `issued_at` source) later -> a late `issued_at`. A rescan of an already issued bucket is blocked in the app before any request (`Bucket X is already issued`), only after the list refreshed.

The screen lists the entries saved in this session with their time (`r.at`, client-side list).

The user stamp is the logged-in USER (`owner`), while grader/packer are Employee picks - the logged-in user is not necessarily either of them. `Bunch Handover` has `track_changes = 0`; 0 rows on the local site.

* Offline: none; a failed POST just shows the message and the worker re-enters.
* Floor sees: only its own session list. Nobody sees handover totals vs packing progress.

### 1.4 Packing ("Packing Entry"): bunch scanning, box building, packing guide, under-pack, bypass, mixed boxes, quality issue
* Files: `app/packing.tsx` -> `features/packing/PackingScreen.tsx` (1397 lines), `QualityIssueSheet.tsx` (437), `state/karen-packing-store.ts` (1247), `state/karen-packing-quality-store.ts`, `api/karen-packing-api.ts`, `api/karen-packing-quality-api.ts`, PDF helpers `core/pdf/*`.
* Who: packers (Employee designation Packer) and line supervisors working on a shared or personal phone; the logged-in USER is stamped, not an Employee. No role gate.
* Order picker: `GET fetchPicklists` (`api.py:2906`, params `date` default tomorrow, `station`). An OPL is LISTED ONLY IF: docstatus = 1 (submitted), Sales Order delivery_date = the date, stock at this station's location, AND (`issued stems >= Production Settings pack_waiting_replacement_pct` (default 50) OR `pack_issued_now = 1` OR every bucket issued), AND it is on a Packhouse Schedule (or its farm is an "own packing farm" such as Karen, or Production Settings `show_unscheduled_in_packing`). Capped at 500 by `opl.creation DESC`. Sort: not-100%-packed first, scheduled before unscheduled, then sequence, team. Each row shows `order name - varieties(lengths)`, corner badge `<Team> #<seq>`, sub-line `OPL - customer - NN% issued (x/y bkt) - short NN% - Issued NN% (when <100) - NN% packed`.
  The "waits_for" field the server returns is mapped (`karen-packing-store.ts:44,358`) but NOT used by the screen: no greying, no banner - the packer only learns of the sequence rule from the refusal below.
* Steps for a SPRAY / non-standard order (item group not "Standard Roses"; scan mode):
  1. Pick order -> `GET get_pick_list_with_farm_pack_list` (`api.py:4240`) returns the OPL lines, the existing Farm Pack List rows (stems per box per variety), and the Packing Guide (planned boxes, packrate per box, mixed flags, bouquet recipe/image) plus the issued cap.
  2. The screen is on "Box 1" (`currentBoxId` starts at 1; `selectOpl` resets it, so a resumed order always reopens on box 1 - the worker must tap the box breakdown to move on; boxes advance automatically after a pack that fills the box, `maybeAdvanceBox`, with a beep).
  3. Scan a bunch QR (JSON with `bunch_id`, `variety`, `bunch_size`). The app does client checks (below), then `POST fetchStockEntryByBunch` (`api.py:3083`, grading Stock Entry lookup by `custom_bunch_id`), then `POST createOrUpdateFarmPackList` with one item (`bunch_qty` 1, `box_id`, `bunch_id`). Then `GET get_pick_list_with_farm_pack_list` again to refresh tallies (so every scan costs 3 round trips).
  4. Toast "Packed successfully". The server's own response (`fpl_submitted`, `box_labels`, message "Fully packed -- Farm Pack List submitted and Box Labels generated.") is IGNORED by the app (grep `fpl_submitted|box_labels` in `src/`: only type fields). The packer is never told that the order completed or that labels now exist.
* Steps for STANDARD ROSES (manual entry): choose the variety chip (when several lines), type a bunch count (the field is clamped to `min(order remaining, room in the box, issued room)`), tap Pack -> `createOrUpdateFarmPackList` with `bunch_id: null`, `bunch_qty = n`. No scan, no bunch identity: one tap can add many bunches to a box - this is the "bulk entry" case for timestamps.
* Mixed box / mixed bunch: for a mixed BOX the guide gives `Target per Box` per variety (`planned stems / planned boxes`, `targetPerVariety`) shown with a tick when met; for a mixed BUNCH the "Bouquet Guide" card shows the spec photo (fetched through `fetch` with the cookie, converted to a data URI because RN Image can't send the cookie), the per-bunch colour/variety/stem recipe, and "Build each bunch to match the photo". Manual entry chips are labelled "Bunch component".
* "Packing issue" panel (collapsed): (a) **Bypass packing** (checkbox) - for a bunch that cannot be scanned (damaged/missing QR or ungraded): choose a reason from `GET getPackingBypassReasons` (master `Packing Bypass Reason`; local has some, 4 logs) and a bunch count -> same caps as manual entry -> `createOrUpdateFarmPackList` (bunch_id null) THEN `POST createPackingBypass` (`api.py:1622`). The two calls are not atomic: if the second fails the worker sees "Packed, but the bypass log failed: <msg>" and the stems are already in the box with no log. (b) **Report under-pack** - choose a reason (`GET getUnderPackReasons`, master `Under Pack Reason`, 8 locally), tap "Close box as under-packed" -> `POST setPackListBoxUnderPackReason` (`api.py:1505`): sets `Farm Packlist Item.under_pack_reason` on every row of that box via `db.set_value` (no time/user stamp of its own), then `sync_and_maybe_submit_fpl` (so closing the LAST box short can submit the FPL and create the labels). The app then marks the box CLOSED in memory only (`closedBoxes`, lost on reselecting the order/app restart: after a restart the box shows its stems again and the server alone decides). (c) **Report quality issue** - opens `QualityIssueSheet`: choose the issued bucket/line, defect (Wrong stem length / Disease / Pest / Other, from `quality_issue_lines`), number of bad stems, replacement bucket from this station's farm (`quality_replacement_options`), submit -> `POST upande_packhouse.api.packing_quality.report_packing_quality_issue` (`api/packing_quality.py:319`; rejects the stems via a "Packhouse Rejects" Stock Entry, allocates + issues a replacement at once, records a `Bucket Replacement` reason "Quality issue" directly `Discarded`). Details in 02_quality_rejects.md section 1 row B. Errors: `No bucket has been issued to this order yet.`, or the server `message`.
  The packing-reject approval flow (`api/packing_reject.py: record_reject / approve_replacement`, Packing Supervisor) is NOT reachable from this app - there is no "packing supervisor" screen in this repo (grep `packing_reject` in `src/` and `app/`: none). Supervision happens on Desk or in the separate Quality app.
* Gates (verbatim messages). Client-side first (no request, only recorded on-device via `recordLocal`, `core/debug/debugLogStore.ts`, never sent to the server):
  `Still submitting the previous scan - please wait.`; `Select an order before scanning.`; `Box N is closed (under-packed). Switch to the next box.`; `Failed to decode QR.`; `Valid bunch QR required.`; `Only P% is issued - pack the rest once more stock is issued (x of y stems packed).`; `Box N is full (R stems). Switch to the next box.`; `<variety> target reached in Box N (T stems max)` (mixed); `This bunch has already been packed.` (same session only: `scannedBunchIds` is in memory); `You cannot pack a discarded bunch.`; `The bunch has already been packed.`; `Bunch not graded. Perform grading scan first.`; `Variety (X) not in pick list.`; `Size (UOM) invalid for X.`; `Bunch graded 50cm but X on this pick list needs longer. A bunch can be packed shorter, never longer.`; `Stem length (L) mismatch for X.`; `X (L) is already fully packed.`; for manual: `Enter a valid number of bunches.`, `X is already fully packed.`, `Box N has room for k more bunch(es). Switch to the next box.`, `Cannot exceed k remaining bunch(es).`; bypass: `Pick a reason first.`.
  Server-side (`createOrUpdateFarmPackList`, `api.py:994-1490`): `Sale Order ID is required`; schedule order `Schedule order for team {T}: pack #{n} first. #{n} isn't fully packed yet, so #{seq} can't be packed before it.` (title "Packing order", rule `_schedule_blockers(opl,"pack")`, done = `PACK_DONE_SQL` (`api.py:3243`): FPL submitted, OR a started draft FPL on an order with buckets marked not found (pack-while-waiting), OR an only-partly-issued order whose every issued stem is packed; bypass = Production Settings `allow_pack_out_of_sequence`); `Invalid or missing item list`; `This bunch has not been graded in the system. Perform the grading scan on it to enable packing`; `All scanned bunches have already been packed: <ids>`; `Stem length mismatch: bunch X is graded ... A bunch can be packed into a shorter length, never a longer one.`; `Over-pack blocked for <item> (<len>): N stems ordered, M already packed - only K more allowed.`; `Over-pack blocked: box B for <item> (<len>) holds P stems (a already in it, only k more allowed). Use another box.`; `Only P% is issued - pack the rest once more stock is issued (x of y stems packed).` (class `IssuedCapError`, title "Not issued yet"); `No valid entries to process`; `Error processing packing: <e>`.
* Records (per pack call): `Farm Pack List` (ONE per OPL): first call `insert()` (draft; `creation`/`owner` = first packer), later calls `doc.save()` (moves `modified`/`modified_by` and, because FPL has `track_changes=1`, writes a `Version` row per save - see 5.2). Rows are MERGED by key `(item, length, uom, box_id)`: `bunch_qty`/`stock_qty` increase on the same row (`api.py:~1330-1346`), the row `creation` = first add. Scanned bunches also get `Stock Entry.custom_scanned_packing = 1`, `custom_opl_scanned = <opl>` (`db_set`, so `Stock Entry.modified` ~ pack time of that bunch - spray only). FPL auto-submits when `fpl_pack_blockers` is empty (every Packing Guide `(box, variety)` has packed >= planned stems, boxes with an under-pack reason skipped, `farm_pack_list.py:89-135, 172-215`) -> `farm_pack_list_on_submit` -> Box Labels (`box_label.py:sync_box_labels_for_fpl`). Every call also writes an Error Log row titled "Packing payload" (`api.py:1000`), see 5.3.
* Offline/retry semantics: no queue. `createOrUpdateFarmPackList` is NOT idempotent for manual entry: a retry (after a lost response/timeout) re-adds `bunch_qty` to the same row; the over-pack guards (order total per item+length, per-box packrate) are the only brake, so a duplicate lands silently whenever capacity remains. For SPRAY scans the `custom_scanned_packing` flag makes a retry safe (`Skipped already packed`). The app's own guard is only the `submitting` flag (re-entrancy, added after a race that produced Box Labels from a stale snapshot - comment `karen-packing-store.ts:661`). The 30 s axios timeout can fire while the server is still committing, so the app may show an error for a pack that succeeded; the next `reloadGuide` shows the truth. Timestamps are server time at request arrival, so a slow network delays them by seconds, never by hours - the "late timestamp" risk is workflow (bulk entry after the fact), not sync.
* What the floor sees: per box `stems / packrate` bar with ACTIVE/FULL/CLOSED tag, per-variety targets (mixed), "Order lines" table Variety/Len/UOM/Req/Pack (bunches), Box breakdown (stems per box per variety), `NN% packed`, `Issued NN%` cap tag and "wait for more stock to be issued", "Order data issues" alert (no packrate, no box count, planned stems vs boxes x packrate do not reconcile). Home dashboard (0.1) gives boxes packed vs required per team and top/bottom packers.

### 1.5 Box label printing (inside Packing; there is no separate screen)
* UI: print FAB (bottom right) on the Packing screen -> modal with label width/height mm (defaults 210x297 = A4, matching the Box Label print format) -> `POST generateBoxLabelsPdf` (`api.py:6639`) -> app writes the base64 PDF to a file and opens the OS print/preview sheet (`core/pdf/pdfDownload.ts: writeBase64PdfToFile, previewPdf`). A second FAB "Saved labels" reopens earlier PDFs for that OPL (`core/pdf/boxLabelsHistory.ts`, AsyncStorage key `box_labels_history`: `{path, filename, count, savedAt}` per OPL, DEVICE-LOCAL, never sent to the server).
* What it prints: ALL `Box Label` rows of the OPL (one page per box, box_number order) through the "Box Label" print format, regenerated each time. There is no per-box print and no reprint-of-one.
* Gate: labels exist only after the FPL is submitted, i.e. after EVERY box of the OPL is complete or under-packed (see 1.4). Before that the worker gets `No box labels found for <OPL>. Pack at least one box first.` - which is misleading (one box is not enough; the whole order must be done). So a packer who finishes boxes 1-5 of 8 cannot print 1-5. For an order sent to packing early ("Pack while waiting", capped by issued stems) the FPL cannot complete until the rest is issued and packed, so labels for the finished part are not printable.
* Not captured: print time, who printed, how many times, printer/device, whether the paper label was ever stuck on the box. Printing is done by phone -> OS print sheet (printer unknown to the system). `Label Print` doctype exists but belongs to the bucket/bunch QR label generator (`server_scripts/gen_label_id.py`), not box labels. The saved-PDF `savedAt` exists only on the phone. Only proxy: `Box Label.creation` (= FPL submit time) for "labels became available".

* Offline: none; a retry of the same scan returns "already in precooling" (duplicate-safe, the original `precooling_in_at` is kept).

* Who: dispatch cold-store pickers. No role gate.

Stop pairing of plan rows to OPLs is positional (comment `api.py:~2400`: "no field linking a Loading Plan Item to a specific OPL"), so counts for split deliveries are best-effort [flag for dashboard: do not re-derive stops this way].

## 3. What the app does NOT capture (no stamp, bulk, override or paper)

1. Issue scan: `Pick List Item.issued` is set with `db.set_value` - no time, no user. `issued_at/issued_by` are backfilled by a 5-minute job from `modified/modified_by` (can be minutes late, `issued_by` = last editor not necessarily the scanner) [01 step 3]. Rows issued before the field existed have none. Lost-response rescans move `modified` later.
2. "Issued offline" (`issued_offline = 1`): physical hand-out happened off-system (verbal/paper); the app records only the later reconciliation, not when the bucket really left (Mark issued offline stamp = `modified`). `Bucket Replacement` rows record Missing/Damaged/Wrong variety/Issued offline reasons.
3. Complete short: the app never sends a `reason`, so the Info comment has no reason text; the comment's creation + owner is the only stamp. Pack while waiting: `pack_issued_now` is set with `update_modified=False` (no time); only the Info comment has time/user.
4. Packing, standard roses: bulk by design - a count typed once, no bunch identity, no per-bunch time; what a "box" means is whatever the packer typed under a box number. Per-box completion time does not exist (box labels are all created at the FPL submit instant). Per-save times exist only in `Version` (5.2).
5. Packing teams that pack on paper first and key the sheet afterwards (Team A/B, Jamafa per the coordinator's production analysis in 01 section 1.1 [PROD, not verifiable locally]): all timestamps are data-entry time.
6. Box number is chosen on the phone (`currentBoxId`), resets to 1 on every reselect, and `closedBoxes`/`scannedBunchIds` are in memory only - restart/handover between workers loses them; the server's guards then decide.
7. Bypass log vs the pack are two calls (non-atomic); a bypass pack with a failed log has no record that it was a bypass (only `bunch_id` null, which is also true for all standard roses).
8. Under-pack reason: row-level `db.set_value` on `Farm Packlist Item` - no time or user; closing a box short just sets a flag on its rows (the FPL `Version` row for that save is not created by `db.set_value`; only a later `doc.save()`/submit gives a `Version`).
9. Box label printing: no time, user, count or printer (1.5); the paper label being attached to the box is not recorded.
10. Precooling "in": time yes (`precooling_in_at`), user only as `Box Label.modified_by` which the next scan overwrites. No precool OUT scan any more; room dwell = `precooled_at - precooling_in_at` but `precooled_at` is actually the staging time. Precooling `duplicate` scans (a worker re-scanning) are not logged anywhere.
11. Staging: time = `precooled_at` (no `staged_at`), user = overwritten, location = free text.
12. Loading: `Box Label.loaded` has no time/user; time/user live on `Loading Sheet Item.creation/owner`; which truck is not recorded (`vehicle` empty, 0/16 rows locally); temperature blank = 0.
13. Dispatch: only `Loading Sheet.location_departures {seal, at, by}`; the Delivery Note is a DRAFT (its submit time is another person's action).
14. Bunch Handover: manual count, not tied to orders, buckets, boxes or the packer's actual packing.
15. Shift / attendance / break / idle time: none in the app (section 4). The app does not know who is physically at which station beyond the logged-in user.
16. Waiting itself (queue time, blocked time) is never recorded; client-side validation refusals are only in the on-device debug log (`recordLocal`, max 300 entries, `core/debug/debugLogStore.ts:14`, never uploaded).
17. Manual overrides that exist: Production Settings `allow_issue_out_of_sequence`, `allow_pack_out_of_sequence`, `show_unscheduled_in_issuing/packing/scheduler`, `pack_waiting_replacement_pct`, `takt_time`; Desk "Submit" of an incomplete FPL still creates labels; Desk-submitted DN; Desk edits of Pick List Items. None of the toggles is time-stamped except via `Version` of the Single doctype (if tracked [UNCERTAIN]).

## 4. Team mechanics

* **A worker does not belong to a team in the app or in the data.** The app has no team on the user, no team selection at login, no per-user filtering. `User`/`Employee` carry no packing-team field (checked: no `team`/`packing` custom field on Employee or User, and `getPostHarvestStaff` filters Employee only by farm "Post Harvest" and designation). Teams exist only on ORDERS: `Order Pick List.team` (Link -> `Packing Teams`, the master has 5: Team A, Team B, Eldama, Jamafa, Bravo; production OPLs also carry "Eldama A/B" that are not in the master, 01 doc), `Box Label.team`, and `Packhouse Schedule.team`. `Pick List Item.team` exists but is empty on every row locally (6065/6065) and the API ignores it.
* How the app filters by team: the team chips on Scheduler / Issuing / Packing / Dashboard are a client-side FILTER over the list the server already returned (`selectedTeam`, e.g. `karen-issuing-store.ts:setTeam`, `PackingScreen.tsx filteredPicklists`). The chip list is the canonical `Packing Teams` master from `GET getPackingTeams` (`api.py:4150`, loaded once per session) with a per-chip count of today's orders (0 allowed). Nothing remembers the chosen team; it resets on each screen visit/date change. So a packer sees every team's orders; the filter is a convenience. Consequence for attribution: who packed an order is `Farm Pack List.owner` / `Version.owner` = the phone's login, which may be a personal login or a shared team login [UNCERTAIN: not determinable from code; ask ops].
* "Team schedule order" enforcement: `Packhouse Schedule` (one per team per date, child `Packhouse Schedule Order(order_pick_list, sequence)`). `_schedule_blockers` (`api.py:3266`) refuses issue #n until every EARLIER sequence of that team at the SAME stock location is fully issued (not-found buckets excluded), and refuses pack #n until earlier ones are pack-done (`PACK_DONE_SQL`, `api.py:3243`). Teams never block each other; Karen and Ravine orders never block each other. Bypass flags in Production Settings. Enforcement is server-side only, at scan/pack time; the lists are not greyed. The sequence itself is machine-ranked: `rank_schedules` (cron every 5 min, `api/remote_transfer/scheduler.py:160`) re-sorts each team's rows by stock tier (issued -> at hub -> remote farm) with own-farm (Karen) orders keeping their slots; only `sequence`/`idx` change (`update_modified=False`). A supervisor's "#1" can therefore change during the shift, and the old `OPL.schedule_number` is overridden in the app by `Packhouse Schedule Order.sequence` (`getSchedulerMeta`, `api.py:4087`). The legacy `setSchedulerOrder` drag-order is unused.
* "Unassigned": the literal default of `PackingItem.team` in the Issuing store when the packing-list row has no team (`karen-issuing-store.ts:298` `r.team ?? 'Unassigned'`; the server sends `opl_team.get(opl) or "Unassigned"`, `api.py:3839`; the Home dashboard also buckets teamless OPLs as "Unassigned", `api.py:6512`). It means the OPL has no `team` set (allocation writes the team once, "first allocation wins", 01 step 1; locally 10 of 1110 submitted OPLs). The Issuing screen hides it (`orderTeam` excludes 'Unassigned', `IssuingScreen.tsx:77`). Unassigned orders never appear under any team chip, and in the Scheduler/dashboard they show with no team. They are also usually not on a team schedule, hence not listed at all unless the unscheduled flags are on. For the dashboard: bucket "Unassigned" separately and show it as a data-quality item.
* Login / shift / attendance: login is `POST /api/method/login` (email + password, or biometric replaying the stored password), session cookie `sid` kept in AsyncStorage; no shift, clock-in, station check-in or attendance concept. "Logout" (side menu) is soft: it clears only the in-memory session flag (`useAuthStore.logout`), keeps the cookie, and on the next cold start `hydrate` re-reads the cookie, so the app reopens as the previous user unless the biometric lock is on (`forgetDevice` is Settings only). On shared phones the stamped user can therefore be the previous shift's user [UNCERTAIN: depends on how workers actually use it]. The station (farm + greenhouse) is a DEVICE setting, not a login attribute; it drives the Karen vs Ravine scoping and the Loading screen. Frappe records every login (`Activity Log`, operation Login/Logout/Failed, user, IP, time) - the only shift-start/end proxy.
* Roles: fetched at login, cached, never used (see 0). Server roles of interest present locally: Packing Supervisor (129 users), Assistant Packhouse Manager (44), Stock User (223), Stock Manager (58), Quality Manager (45). `Order Pick List` write for Packing Supervisor / Assistant Packhouse Manager per 02 doc.

## 5. Data the app already produces that nobody reads

### 5.1 Offline queue / sync stats: there are none
No offline queue, retry, backoff, outbox, local DB of pending actions or sync status (grep `queue|retry|outbox|sync` across `src/`, `app/`: only the unrelated "issued offline"/"in queue" labels). Network handling is a banner (`core/network/store.ts`: connectivity poll every 15 s online / 6 s offline via `expo-network`, flips offline after 2 consecutive API failures `FAILURE_THRESHOLD`; BUT `notifyApiSuccess/Failure` are never called by the api client (grep: only defined in the store) so the "offline after 2 failures" path is dead code and the banner reflects only the OS connectivity check [UNCERTAIN: verified by grep only]) and an error toast per failed action. Consequences: (1) an action done while offline is NOT stored - the worker must redo it, or does the work and forgets (so server timestamps lag the physical event by the outage and are sometimes missing altogether); (2) there are no queue stats to mine; (3) duplicates arise only from a worker retrying after a lost response (manual packing double-add is the realistic one, 1.4). All server-side timestamps are therefore "time the request arrived", never a client time (the app never sends a client timestamp, apart from the optional `handover_time` it doesn't send).

### 5.2 Server records that already hold the stream (unread)
1. `Version` rows of `Farm Pack List` (doctype `track_changes = 1`; `Version` is NOT in `Logs To Clear` locally, so it is kept): every `doc.save()` in `createOrUpdateFarmPackList` writes `{creation, owner (= packer user), data.row_changed/added: [pack_list_item, rowname, [[bunch_qty, a, b],[stock_qty, c, d]]], box_id/item in added}`. Local: 572 versions for 17 FPLs (e.g. FPL-2026-00011: 167 saves in 6 minutes), 278 with child-row diffs. This IS a per-pack-event stream with a user and a time (one event per call, i.e. per scan for spray, per tap for standard) - it contradicts "no per-scan event" in 01 (the child row alone has none, `Version` does). Cost: JSON parse; it holds one row per save, only for FPL/OPL (OPL versions record docstatus flips, i.e. OPL submit time = when issuing allowed packing, and `short_accepted`). `Bucket Request Trip` versions record status changes with `dispatched_at` etc. `Box Label`, `Loading Sheet`, `Bunch Handover`, `Packing Bypass Log` have `track_changes = 0`.
2. `Error Log` rows written by the endpoints on EVERY call: title (stored in `method` in v16) "Issuing from coldstore payload" (`api.py:4883`, payload bucket/sale_order_item/opl_name, owner = scanner user, creation = time), "Packing payload" (`api.py:1000`, full item list), "Staging Payload" (`api.py:1813`), "Grading Payload"/"Grading Debug"/"harvest payload" from other flows. Local: 11 / 62 / 1 rows. Caveat: `Logs To Clear` keeps Error Log only 14 days, and the table is noisy (63,893 rows locally, 1,666 "Grading Debug"). Useful as a real-time tail for "last scan seen at HH:MM by user" and, together with the error titles `Farm Pack List Packing Error`, `Coldstore Issue Error`, `Bunch Handover Error`, `record_loading_scan error`, `createOrUpdateDispatch (DN) error`, `FPL auto-submit failed`, `Issue: submit for packing failed`, `Issue -> Packhouse: nothing moved`, `Stage -> Dispatch: nothing moved`, `Load -> Truck: nothing moved` (stock-hop failures), as a health signal. Do not build analytics on it (retention, volume, free-text).
3. Stage stamps with user on `Pick List Item`: `issued_at/by`, `shelved_at/by`, `arrived_at/by`, `left_farm_at/by`, `loaded_on_truck_at/by`, `loaded_in_trolley_at/by`, `not_found_at/by` (3154 issued rows locally, 2731 with `issued_at`); `Bucket Request Trip.requested_at/by, released_at, dispatched_at, arrived_at, received_at`; `Box Label.precooling_in_at, precooled_at`; `Loading Sheet Item.creation/owner`; `Loading Sheet.location_departures`.
4. `Packing Bypass Log` (`packed_by`, bunches, reason, traceability to greenhouse/harvester/supervisor), `Under Pack Reason` on FPL rows, `Bucket Replacement` (reason/status/reported_at/resolved_at), `Packing Reject Log`, OPL Info comments (`Comment` rows: "Completed short by ...", "Packing what was issued: P% issued ...", 3 locally) - each with owner and time.
5. `Mobile App Version Log` (`user, app_version, platform, device_model, reported_on`): one row per user per day, updated in place. The app sends `device_model` as the constant "Android device"/"iOS device" (`src/core/version/index.ts:70`), so there is NO device id/model/IMEI/serial and nothing to say two users share a phone. The app reports at most once per device per UTC day after login/unlock (`reportVersionIfDue`, key `versionLastReportedOn`); `reported_on` = last report of the day by that user across devices. Useful for: who opened the app today, app version drift (local: 4 users, all 1.0.0), Android vs iOS. Not useful for shift hours.
6. `Activity Log` (Login Success/Failed/Logout, `user`, `ip_address`, `communication_date`; local 1,292 successes, 4,492 failed attempts; retention 90 days) and `User.last_login/last_active/last_ip`: shift-start and failed-login (wrong password / typing trouble) signals. All Frappe web logins share this log, not just the app; the app is identifiable only indirectly.
7. On-device only, unreachable: the in-app debug log (300 request/response + client-validation entries, screen `debug-log`), saved box-label PDFs history, last station/dispatch location. Nothing uploads them. If the dashboard needs "refusal reasons by station" a tiny `POST logClientEvent` in the app would be required; today only server-refused calls leave a trace (as `Error Log` for exceptions, or nowhere for `status:error` 200 responses such as precooling/staging/loading refusals, which are not logged at all).

### 5.3 Error-message census available from code (what workers can be told)
Server `frappe.throw` messages (HTTP 417/ValidationError) are mapped to plain text; those returned as `{status:"error"}` with 200 are shown but never logged server-side (precooling, staging, loading, dispatch gates) - so "how often are workers blocked by X" is answerable only for: schedule-order 409 (issue), `Over-pack blocked`, `Only P% is issued`, `Schedule order ... pack #n first` (these are `frappe.throw`s: no Error Log row for ValidationError in `createOrUpdateFarmPackList` except via the generic `frappe.log_error(title="Farm Pack List Packing Error")` in the except block - which IS written for every refusal there since the `try/except Exception` catches them; so "Farm Pack List Packing Error" rows are a count of refused pack calls, `IssuedCapError` excluded via `raise` first) and "Coldstore Issue Error" (500s only; the 409 schedule/waiting/already-issued responses are written as responses, not errors).

## 7. Corrections / cautions for other docs and the mockup

* 01 section 1 step 4 "No per-scan event/log table" - there is one in practice: `Version` rows of `Farm Pack List` (5.2.1) and `Error Log` "Packing payload" (5.2.2); child-row `creation` is still only first-add.
* 01 step 9 lists `Loading Sheet Item(..., vehicle)`: the field exists but `createLoadingEntry` never fills it.
* The floor already sees: queue order and issued % (Scheduler/Issuing/Packing), per-box fill, box-stage counts (Precooling), per-stop loading (Loading), loaded vs required (Dispatch), packed-vs-required per team and a packer league (Home). The mockup should add what none of these show: age/waiting time per stage, stalled reasons, cross-stage joins per order (issue -> pack -> labels -> precool -> stage -> load), team-level sequence blocking, data-quality (Unassigned, unscheduled, no packrate), and the off-system gaps in section 3.
* Safe to rely on: `precooling_in_at`, `precooled_at` (= staging), `Loading Sheet Item.creation/owner`, `location_departures.at/by`, FPL submit (`Box Label.creation`), FPL `Version` stream, `Pick List Item.*_at/_by` (with the issued 5-minute lag). Not safe: per-box packing time, label printing, which truck a box rode, who really issued, any time for bulk-entry teams.
