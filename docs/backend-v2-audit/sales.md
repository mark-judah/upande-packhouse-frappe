## Page: Sales Order (/sales-order-v2) — API: api/sales_order.listSalesOrders, getSalesOrder, saveSalesOrder, submitSalesOrder; spec_autofill.get_spec_fill_data / build_spec_rows; api/order_import.*; sales_order_engine (hooks)

### What the page shows and how it's computed (brief)
- **List and KPIs** (Orders / Drafts / Boxes / Stems): `listSalesOrders` (api/sales_order.py:304) returns at most 200 Roses SOs, newest `modified` first, and **includes cancelled ones**. The page then filters by status and sums the stored `custom_total_boxes` / `custom_total_stems` (`www/sales-order-v2.html:269-277`, `PH.sum`).
- **Editor**: saved lines are loaded into `SPEC_ROWS` tagged `_saved`. New manual lines are "cards"; new spec lines come from `build_spec_rows`. The live editor KPIs (Boxes / Bunches / Stems / Est. subtotal) come from the client-side `computeTotals()` (html:513-543).
- **Save**: `saveSalesOrder` copies every header field, then runs `doc.set("items", [])` and appends only `spec_rows` + `manual_rows` (api/sales_order.py:504-512). The engine hooks then recompute `qty`/`stock_qty`/`custom_ordered_quantity`, pricing and the order totals.

### Performance profile
- `listSalesOrders`: 1 query, 200 rows, small table. Fast. `getSalesOrder`: one `get_doc`.
- `saveSalesOrder`: about 5N of this app's own queries per save on top of ERPNext's validation: Item Price get_value per line, Item.sales_uom twice per non-spec line (validate 4 and 4b), Item.custom_color plus Specifications.max_colours per mixed-box line, and per manual row Item.stock_uom + `_ensure_bunch_uom` + `_ensure_packrate`. A 24-line order is roughly 150 own queries. Batch all of these into IN-queries.
- `get_spec_fill_data`: about 1.2 s wall time via `bench execute` (about 1 s of that is bench start-up). `variety_availability` aggregates **all** of Shelf Item (3,872 rows) in a derived table before filtering. Fine now; push the filter inside the subquery.
- Item Price has no composite index on (item_code, price_list, custom_length); there are single indexes on item_code and price_list. 22k rows, OK.

### v2 backend design notes
- **One server function `so_totals(so_rows)`** used by the save hook, list, KPIs, editor preview, and dashboards. stems = Σ line_packrate × boxes. boxes = Σ per key, where key = mixed ? (spec+length | bunch_group | mix_group) : the row itself. Validate that all rows of a key share boxes (rule 6 extended to spec keys).
- **Totals at read time in SQL** (one aggregate with a window function, as in canon.sql) so stale stored fields can never leak. Otherwise backfill the stored fields and recompute on `on_update_after_submit` too.
- **List endpoint**: server-side filters (status, date range, customer, text), a separate unpaginated KPI aggregate excluding docstatus 2, and pagination.
- **Save**: diff-based line update (SO-1); server-assigned group ids (SO-11); fx from the document's conversion rates (SO-9); packrate/UOM consistency check (SO-10).

## Page: Specifications (/specifications-v2) — API: api/specifications.listSpecifications, getSpecification, saveSpecification

### What the page shows and how it's computed (brief)
`_group_into_bunches` turns Box Item and Approved Variety rows into bunches → colour rows. The client shows a row total of `bunches_per_box(bunch) × stems_per_bunch(row)`, a bunch subtotal, and a "Spec total N stems" (html:352-353). KPIs come from the 200-row list.
