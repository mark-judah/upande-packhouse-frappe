# Bucket Journey: authoritative event catalog

Scope: everything the mobile apps and server code can do to a bucket, where each event is stored, how to key it to a bucket and a cycle, and what the current Bucket Journey v2 tab (and its v1 reader) captures. Read-only research; nothing was written to the database or code. Evidence is from the local site `kaitet.local` (data to 2026-10-13) and the code under `apps/`.

Abbreviations: **AG** = `upande_agriculture/upande_agriculture/mobile/api.py`; **Q** = `upande_quality/upande_quality/mobile/api.py`; **PH** = `upande_packhouse/upande_packhouse/mobile/api.py`; **TS** = `upande_packhouse/upande_packhouse/api/remote_transfer/transfer_scheduling.py`; **SA** = `upande_packhouse/.../page/sales_allocation/sales_allocation.py`; **SM** = `upande_packhouse/upande_packhouse/stock_movement.py`; **RJ** = `api/v2/rt_journey.py`; **V1R** = `api/remote_transfer/bucket_journey.py` (`getBucketJourney`); **V1JS** = `templates/remote_transfer/bucket_journey.html` (builder at lines 1184 trackBucket, 1248 buildJourneys, 1299 matchJourney, 1395 journeyByDate, 1454 journeyStatus).

## 0. Read this first (cross-cutting facts)

1. **Live logic may be DB Server Scripts, not the repo code.** The local DB holds Server Scripts (type API) with the same method names as the Quality-app functions: `createShelvingEntry`, `createReceivingStockEntry`, `releaseFromQuarantine`, `submitBatchQuality`, `getTraceability`, `getBucketTrace`, `clearShelfItem`, `getShelfItemsForClearing` (dumped for reading to `/tmp/claude-1000/-home-jk-Projects-upande-local-bench-v16/17d427cc-b5a7-41af-a956-596b17b9ecd7/scratchpad/ss/`). Frappe serves a bare Server Script API method before a whitelisted Python function of the same name. The Python in `Q` is the v16 port of those scripts. I did not diff them line by line, so treat per-line details of those functions as "port of the live script, verify before relying on an edge case". `clearShelfItem` exists ONLY as a Server Script (no repo code): it needs role `Shelf Clearer`, deletes the Shelf Item and sets the Shelving Log to `Shelf Cleared` (script text in `ss/Clear_Shelf_Item_(emergency,_role-gated).py`). `createDiscardEntry`, `transferBucket`, `createOfflineIssuingEntry` have no Server Script locally, so the repo code is what runs.
2. **Current journey state is NOT history.** Pick List Item (PLI) flags (`issued`, `shelved`, `in_transit`, `awaiting_transfer`, ...) are overwritten as the order progresses. Per-step timestamps `loaded_in_trolley_at, loaded_on_truck_at, left_farm_at, arrived_at, shelved_at, issued_at` (+ `_by`) exist on PLI (declared in the doctype, written by `api/remote_transfer/transfer_steps.py` stamp/reconcile) but are NULL on all 6055 local PLI rows (0 of 3148 issued rows has `issued_at`), so they cannot be relied on yet. Historic timing comes from Version rows of the Order Pick List (`TS:_pli_flag_times` 3125) and from the Bucket Transfer Event log (empty locally, 0 rows).
3. **Bucket id case.** Collation is `utf8mb4_unicode_ci` (case-insensitive SQL), so `WHERE custom_bucket_id IN (...)` matches any case. But Python-side joins are case-sensitive. Quarantine movements are written lower-case (`bucket_id.lower()` in `Q:7379`, `Q:~9985`): 111 of 112 `Receiving Quarantined`, 55 of 55 `Quarantine Accept`, 2 of 2 `Quarantine Rejects` are lower-case. Harvest rows are mixed (170,095 lower vs 139,556 upper since 2026-08-01). Shelving Log, Discard Request Bucket and PLI.bucket are upper-case only. Always compare `UPPER()` on both sides. Bucket ids are 6-char codes (`8602EF`, `HE3W8B`) plus test ids (`SIM-BUCKET-0012`, `BLK-00823-00082`). No prefix convention to strip.
4. **Spray vs standard.** Spray roses: one mobile scan (`createGradingStockEntry`) creates a Harvesting SE AND a Grading SE, cross-linked (`custom_grading_entry` / `custom_harvest_entry`), AG:324-462. Standard roses: one Harvesting SE (`createHarvestStockEntry`), no Grading SE. A bucket cycle can contain MANY harvest scans (spray: a session of scans) and ends with ONE Receiving SE that claims them all through `Harvesting.custom_receiving_entry` (`Q:1255`).
5. **Backdated receiving.** `createReceivingStockEntry` posts the Receiving SE on the harvest date when the harvest is 1+ days old (`Q:1203-1204`), and the confirm step `no_harvest_on_date` (`Q:1163-1191`) lets a stale bucket be received late. So `posting_date` of Receiving can be earlier than its `creation`; `posting_time` is the clock time of the scan. Order events by `posting_date + posting_time`, and by `creation` as tiebreak.
6. **Quality (QC) results are not keyed to buckets.** `Quality Reporting` has no bucket or batch field (fields listed by meta: control_point, farm, ghouse, variety, stems_received, stems_checked, control_action, quarantined_stems, stems_accepted, stems_rejected...). One Quality Reporting is made per (variety, action) group per batch (`Q:10026+` per-group loop), so a bucket "Accepted" at intake leaves NO bucket-keyed record at all; only Quarantined / Rejected buckets leave stock entries. Local counts: Intake Accepted 28,137, Quarantined 4,170, Packhouse Accepted 358, Packhouse Quarantined 2.
7. **Local data note.** Many tables the journey needs are empty locally: Bucket Replacement 0, Bucket Transfer Event 0, Bucket Request Trip(+Bucket/Order) 0, Bucket Dispatch 0, Packing Reject Log 0, Coldroom QC does not exist. Stem Replacement Log 2, Bucket Reuse Anomaly 4, Bucket Count Bucket 26, Cold Store Stock Take Bucket 60. The catalog below is from code; the "DB evidence" lines say where it was confirmed locally.

### B4. How to place any event into ONE cycle (recommendation)

The current key is `posting DATE` + variety (RJ `match_journey`, `journey_by_date`), which is too coarse because many scans, receivings, shelvings and picks happen on the same date. Better, in this order:
1. **Cycle id = Receiving SE name.** Every Harvesting SE claimed by a receive has `custom_receiving_entry = <Receiving SE>` (Q:1255). Group harvests by it (an unreceived tail = one open cycle). Receiving and its Grading SEs ride along. This also removes the "one journey per scan" explosion for spray buckets.
2. Anything with its own timestamp is placed by FULL timestamp (date + time) between this cycle's start (first harvest `creation`) and the next cycle's start, not by date.
3. Rows that carry explicit cycle fields use them: Shelving Log / Shelf Item (`harvest_date`, `receiving_date`), BAS (`harvest_date`, `receiving_entry`), Bucket Reuse Anomaly (`harvest_stock_entry`), Quarantine SEs (`custom_receiving_batch_id` = the Receiving SE's), Discard Request Bucket (`harvest_date` Datetime, `shelf`), Bucket Replacement (`reported_at`, `order_pick_list`), Pick List Item (OPL + `creation`; picks are made while the cycle's stems are on the shelf, so choose the cycle whose shelving interval overlaps).
4. Variety is a weak key (relabelled by `correctDetails`, multi-variety buckets) and must never DROP a row; fall back to the nearest cycle by time.

## C. Known traps (with local evidence)

### C1. Bucket reuse anomaly (skipped discard/issue shows up in the next journey)

* **Where it is stored:** doctype `Bucket Reuse Anomaly` (`upande_agriculture/.../doctype/bucket_reuse_anomaly`, autoname `BRA-{bucket_id}-{#####}`). Fields: `bucket_id, skipped_step, detected_on, farm, greenhouse, variety, stems, previous_shelf, discard_request, harvest_stock_entry`.
* **Written by:** AG:cleanup_bucket_reuse_anomalies:179 at the first contact of a NEW cycle (every standard harvest AG:720; the first spray scan of a session AG:371-378). It looks for leftovers of the PREVIOUS cycle: a still-existing Shelf Item (never issued) and/or an undischarged Discard Request Bucket row. Skipped step = `Discarding Skipped` if a request row is pending, else `Issuing Skipped`. It then **deletes** the stale Shelf Items and force-sets `discarded=1` on the stale request rows (AG:221-224), writes the anomaly, commits. A third kind `Skipped Transfer` is written at shelving time (Q:2258-2276) when a transfer bucket is shelved while its remote Shelf Item is still on the farm shelf; it has no `harvest_stock_entry`.
* **What it contains:** `harvest_stock_entry` = the harvest SE of the NEW cycle (journey N+1). `previous_shelf`, `variety`, `stems` and `discard_request` describe the leftover of journey N. `detected_on` = time of the first harvest scan of N+1 (or the shelving time for Skipped Transfer).
* **How to attach:** to the journey whose `harvestSEs` contains `harvest_stock_entry` (that is "journey 11" in the user's example); render it as a warning on journey 11 AND as an end-of-cycle "Not issued / not discarded: left on <previous_shelf> (<stems> stems), cleaned up on <detected_on>" on journey 10 (the previous cycle of the same bucket, by order). `Skipped Transfer` has no harvest link: attach by `detected_on` to the cycle that has the Receiving before it; its `previous_shelf` is the remote shelf removed.
* **Side effect that hides the truth:** the cleanup deletes the Shelf Item but does NOT close the Shelving Log row. The previous journey therefore keeps an OPEN `Shelved` log row forever and `journey_status` says "On Shelf" (RJ:331-337). Local count: **1,593** open Shelving Log rows with no Shelf Item; **1,354** of those have a later harvest on the same bucket (reuse) and only **1** of them has a Bucket Reuse Anomaly row, so reuse cleanup is mostly happening WITHOUT an anomaly record (cause not established: older data, desk edits of the Shelf form, or this guarded code path being skipped; unsure). Other causes: 154 re-shelved later with no harvest, 82 "other", 2 discards (DISCARD-TEST-001/002).
* **Not shown today:** RJ and V1R never read the doctype (`grep anomal` in RJ, V1R, rt-journey-v2.js, v1 template: nothing).
* **Local real example:** bucket `SIM-BUCKET-0012`, anomaly `BRA-SIM-BUCKET-0012-02933` (`Issuing Skipped`, detected 2026-09-19 23:40:57, harvest SE `MAT-STE-2026-100009403`, previous shelf `SIM-KAPKOLIA-2026-00250-01`, 80 stems). v2 output: journey 9 (harvest 23:40:56, the one carrying the anomaly) shows only Harvest/Grade/Receive; journey 1 (22:31:28) shows BOTH shelvings (23:17:44 and 23:49:59), the Issued step and the Allocation, although the second shelving/issue belong to the cycle of journey 9/10; the first Shelving Log row `qs9n6kl23c` is still open (`removed_on` NULL). This is the date-tie effect: all of journeys 1-8 started the same DATE, `match_journey` keeps the first on a tie (RJ:174 strict `>`), while the pick row goes to journey 10 (RJ:299 "ties pick the later one"). Other anomaly rows: `COOLTEST2-RAD-B01` Issuing Skipped, `OPLTEST-E-BKT-2/3` Skipped Transfer (test ids).

### C2. Several OPLs/orders allocated to the same bucket; why rows slip away

How allocation is stored: **Pick List Item** (one row per box, child of `Order Pick List`, field `bucket`), plus **Bucket Allocation Status** with child **Bucket Allocations** (per sales order item; `cancelled`, `issued`). PLI is the per-order record; BAS is the per-bucket running total. Replacement re-points PLI rows to another bucket in place (SA:3470-3500).

How v1/v2 assigns pick rows (RJ:289-300 = V1JS:1341-1354): for each PLI row: candidate journeys = journeys whose `variety` equals `row.item_code` (case-insensitive) ; drop the row if none; eligible = those with `earliestDate <= opl_date` (OPL header `date_created`); drop if none; take the latest (ties: the later one). Then the page builds ONE card per OPL parent and prints the FIRST row's `stock_qty` and `issued` (RJ:499-516; V1JS:1668 keeps the LAST row, so v1 and v2 differ). `where_now` uses `opl[0]` only.

Why rows slip away, with numbers (simulated by running `rt_journey.build_v1_journeys` read-only on the 400 busiest multi-OPL buckets of the local DB):
* 3,198 buckets have pick rows; **1,120 have 2+ OPLs** (max 13: `JV1OTG`, 4 varieties; `1BUYY8`: 9 OPLs); 587 buckets have more than one row per OPL (max 20 rows, one per box).
* In the sample: 1,811 pick rows; **1,566 shown, 219 dropped because no journey of that variety exists, 26 dropped because the OPL date is earlier than every same-variety journey**; 127 of 400 buckets lose at least one row. Examples: `L2XS68` 11 rows, 1 shown (OPL-2026-00661 is Furiosa, the bucket's journeys are Red Calypso/Moonwalk/.../Marisa); `53E0AR` 9 rows, 1 shown (OPL-2026-00659 Aqua x8 dropped); `JV1OTG` 13 rows, 11 shown (OPL-2026-00573/00588 Odilia dropped; no Odilia journey: the bucket was relabelled or a multi-variety receive was collapsed to its first item). Variety mismatch causes: `correctDetails` rewrites harvest/receiving item_code in place (#5), multi-variety Receiving shows only item 1, replacement re-points a row to a bucket of another length/variety.
* **277 rows hidden by "one card per OPL"** (13,097 stems) in that sample, e.g. `RDHWGJ` OPL-2026-00038 has 10 rows of 10 stems, shown as one 10-stem card. 336 journeys carry 2+ OPLs.
* **Spray sessions fan out**: a session of 10 scans = 10 journeys of the same variety/date; the OPL goes to ONE of them (the last, by the tie rule) while shelf rows go to the FIRST (the tie rule is the opposite for shelf, RJ:174 vs RJ:299). So an order and its shelf row end up on different journeys.
* Allocation snapshot (BAS): V1R:116 loads the first BAS found for the bucket id (279 BAS rows, 2 buckets have 2). It is current state (not cycle history) and the step time is `BAS.modified`. Only 1 journey gets it (RJ:302-307).
* Caps: V1R `LIMIT 500` pick rows, `LIMIT 800` shelving log, `LIMIT 200` shelf items/discards, `LIMIT 4000` stock entries (`MAX_ENTRIES*2`), `remote_transfers` limit 5 (TS:3167): a busy bucket silently truncates.
* Replaced buckets: the OLD bucket's pick row no longer exists (re-pointed), so the old bucket's journey loses its order entirely; the NEW bucket inherits the row's original `creation` (when the order was first allocated to the OLD bucket) as its pick time.
* Timestamps for the transfer stages are Version-log derived and the new PLI `*_at` stamps are all NULL; the "Picked" step time is `pli.creation`, not an issue time.

## E. Test plan: synthetic bucket `JTEST-001` (not executed; plan only)

### E1. Principles
* Many mobile functions commit (`frappe.db.commit()`), so a savepoint/rollback test does NOT protect. Run on a **scratch copy** of the site (bench restore a backup to `jtest.local`) or accept explicit cleanup (E4). Never against production.
* Call mobile functions in-process with `offline_issue._call(endpoint, payload)` (api/offline_issue.py:213) which swaps `frappe.local.request` for a fake whose `get_json()` returns the payload; run as a real user: `frappe.set_user(<user with roles>)`, because some functions read `frappe.session.user` (`shelved_by`, `reported_by`, `owner`). Functions that read `frappe.form_dict` (`saveTrolleyData`, `getTraceability`, `markRequestedBucketNotFound`) need `frappe.form_dict.update(...)` instead.

For journeys on different days either patch `frappe.utils.nowdate/now/now_datetime/today` with `unittest.mock.patch` (needs patching in each module namespace that did `from frappe.utils import ...`) or insert Stock Entries directly with `set_posting_time=1`, `posting_date`, `posting_time`. Direct inserts are the reliable way to build a timeline; use the mobile call only for the step whose side effects matter (marked below).
* Use same-day journeys on purpose for two of them (to prove the date-tie trap) and distinct days for the rest.
